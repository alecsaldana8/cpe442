Lab 4: Memory Hierarchy and Data Locality

Setup and Measurement Method

Hardware: Apple M2 (8-core). L1 data cache: 128 KiB per performance core (64 KiB per efficiency core). L2: 16 MiB shared across the performance cluster. Cache line: 128 B. Memory page: 16 KiB.

Build: g++ -std=c++17 -O0 -Wall -Wextra (Apple clang 14.0.3) against OpenCV 5.0 (make lab4). No optimization flags, SIMD intrinsics, threads or GPU.

Arithmetic (identical in every implementation): my selected Lab 3 arithmetic is used throughout. Neither equation changes between any of the implementations being compared. - Grayscale: fixed-point BT.709, Y = (218R + 732G + 74B + 512) >> 10 - Sobel: standard 3×3 Gx/Gy kernels, magnitude min(|Gx| + |Gy|, 255) - Border policy: border pixels are skipped, so the output is (W−2)×(H−2)

Excluded from timing: - Video decode and resizing - Buffer allocation: every output, grayscale-frame and row buffer is allocated before the timed loop and reused - Correctness comparison, PNG output and display

Timing procedure: - Timer: std::chrono::steady_clock - Each implementation gets one warm-up pass, then 5 timed repetitions over all 5 frames - Within each repetition the implementations take turns, so thermal or background drift affects them equally - The median repetition is reported - Time per pixel = time per frame ÷ (W−2)(H−2) output pixels

Explanation

Physical layout: C/C++ and OpenCV store 2D data one row after another. Moving one column to the right moves 4 bytes in memory. Moving one row down moves an entire row, N × 4 bytes.

Row-major traversal (consecutive accesses 4 bytes apart): - A 128 B cache line holds 32 int32_t values. - One line fetch serves 32 consecutive accesses, so only 1 in 32 accesses misses. - The hardware prefetcher recognizes the sequential stream and fetches lines before they are needed. - As a result, row-major time stays about 0.95–1.0 ns per element from 1 KiB all the way to 256 MiB.

Column-major traversal (consecutive accesses N × 4 bytes apart): - Once the stride is 128 B or more (N ≥ 32), every access lands on a different cache line, and only 4 of that line's 128 bytes are used before jumping away. - The line is only useful again when the traversal reaches the next column, N accesses later. - If the N lines touched by one column don't fit in L1, they are evicted before that reuse, and nearly every access misses L1. - At 4096 and 8192, the 16–32 KiB stride also means every access touches a different 16 KiB page. That adds TLB misses on top of cache misses. - The result is about 7 ns per element, 7–7.5× slower than row-major.

Spatial locality is what row-major exploits and column-major wastes: row-major uses every byte of each fetched line immediately.

Method: sobelFullAt and sobelFullPtr are the two versions compared. Both: - traverse in row-major order - use the same arithmetic and border policy - read the same precomputed grayscale frames and write into the same preallocated output size

Analysis

Did row-pointer access improve performance? By how much? Yes. Row pointers were 2.68–2.77× faster at every resolution: about 23 ns/px with .at() versus about 8.5 ns/px with pointers. They removed roughly 63% of the Sobel stage's execution time.

Why might calling .at() for each pixel require more work than indexing through a row pointer? At -O0, .at<uchar>(y, x) is not inlined. Each call: - pushes arguments and sets up a stack frame - loads the Mat's data pointer and step[0] from the Mat object - computes data + y*step[0] + x (a multiply and two adds) - returns a reference, which is then dereferenced

The Sobel loop does this 9 times per pixel. The row-pointer version calls ptr() only 4 times per row (three input rows and one output row). After that, each access is a single add and load: rowAbove[x + 1].

Does this experiment primarily measure cache locality, pixel-access overhead, or both? Primarily pixel-access overhead. Both versions touch the same bytes in the same order, so the cache sees an identical access stream. The evidence: - The speedup is constant (about 2.7×) from 320×180, where the grayscale frame is 56 KiB and fits in L1, to 7680×4320, where it is 32 MiB and fits in no cache. - A cache effect would change as the working set crossed cache boundaries; a fixed per-access cost does not. - Time per pixel is also nearly constant across resolutions for each method.

Why is it important that both versions use the same traversal order? It keeps memory behavior the same so that access overhead is the only variable. If one version traversed column-major, it would also pay the locality penalty measured in Part 2. The two effects would then be mixed together, and the speedup couldn't be attributed to either one.

Would the difference remain equally large at -O3? (prediction) No. I expect the gap to shrink to nearly 1× at -O3: - .at() is a small inline template. The compiler would inline it, remove the call overhead, and hoist the loop-invariant row address data + y*step out of the inner loop. - That produces essentially the same code as the manual row-pointer version. - The compiler may also vectorize both loops the same way.

Purpose of obtaining each row through ptr() rather than assuming one tightly packed array: A cv::Mat row is step bytes long, which may be larger than cols × elemSize: - Rows can be padded for alignment. - The Mat can be an ROI or submatrix of a larger image, in which case consecutive rows are separated by the parent's full row width. - ptr(y) returns data + y*step, which is always correct. Indexing data[y*cols + x] is only correct when isContinuous() is true.

My benchmark verifies this. It runs the full-frame and streaming pipelines on a non-continuous color ROI (CV_Assert(!roi.isContinuous())) and asserts that their outputs match each other and the .at() version bit-for-bit.

For a multichannel image, how does the pixel type differ from a single-channel grayscale image? - Grayscale (CV_8UC1): each pixel is one uchar, accessed as at<uchar>(y, x) or ptr<uchar>(y)[x]. - BGR color (CV_8UC3): each pixel is three interleaved bytes (B, G, R), so the pixel type is cv::Vec3b, accessed as at<cv::Vec3b>(y, x). - Through a byte pointer, pixel x's channels are at row[3*x + 0], row[3*x + 1] and row[3*x + 2], as in grayRowFixed. - A color row is therefore 3 × width bytes. Using the wrong template type with at<>() would read the wrong addresses.

Baseline pipeline: color (CV_8UC3) → grayscale frame (CV_8UC1) → Sobel output (CV_8UC1)

Grayscale frame Written by grayscale, then read by Sobel WH Yes: only exists to pass data from grayscale to Sobel
Sobel output Written once by Sobel (W−2)(H−2) No (result)

Reuse in Sobel: - Each output pixel reads the 8 neighbors of its 3×3 window; the center pixel has weight 0 in both kernels. - An interior grayscale pixel is therefore read by up to 8 different output pixels: the ones to its left and right in its own row, and three each in the rows above and below. - Horizontally adjacent outputs share 4 of their 8 inputs (two in the row above, two in the row below), and their 3×3 windows overlap in 6 pixels. - A grayscale row is used by three consecutive output rows.

Is reused data accessed soon after its previous use? - Horizontal reuse happens within a few accesses and always hits in cache. - Vertical reuse happens one full row later, about W bytes of grayscale reads per row in between. At 4K that is about 3.8 KB per row, well within L1. - However, the baseline writes the entire grayscale frame (WH bytes) before Sobel reads any of it. The time between writing a grayscale pixel and first reading it is a whole frame.

Growth with resolution: the grayscale frame is W×H bytes and grows with the pixel count. It no longer fits in the 16 MiB L2 at 8K.

Part 5: Streaming Implementation

pipelineStreaming keeps a single preallocated 3 × W CV_8UC1 Mat (rowBuf), reused across frames, plus three pointers above, center and below into its rows.

  1. Prime: convert color rows 0 and 1 into above and center.
  2. For each output row y = 0 … H−3:
  3. Convert color row y+2 into below.
  4. Compute Sobel output row y from above, center and below, which hold grayscale rows y, y+1 and y+2.
  5. Rotate: oldest = above; above = center; center = below; below = oldest;
  6. The buffer that held grayscale row y has had its last use, so it becomes the destination for row y+3.

Only pointers move; no row data is ever copied.

Edge cases: - First and last rows: handled by priming two rows and stopping at output row H−3, the same "skip the border" policy as the baseline. - First and last pixel in each row: handled by the same sobelRowApprox kernel as the baseline, which reads columns x…x+2 for output x. - Row stride: every color row is obtained with color.ptr<uchar>(y). This was verified on a non-continuous ROI. - Overwriting a row before its final use: below is overwritten only after rotation, at which point it holds a row no future output needs.

Correctness: streaming output matches the baseline bit-for-bit on all 5 frames at all 5 resolutions: 0 differing pixels, max abs difference 0 (the same pixel counts as the Part 3 table).

Part 7: Discussion

1. Why did row-major and column-major traversal perform differently when they processed the same number of elements? They did the same arithmetic but generated different memory traffic: - Row-major reads consecutive addresses, so each 128 B cache line serves 32 accesses and the prefetcher streams lines in ahead of use. - Column-major jumps N × 4 bytes per access. On large arrays each access touches a new line and a new page, uses 4 of the line's 128 bytes, and the line is usually evicted before the next column returns to it. - At 4096×4096, column-major took 6.89 ns/element versus 0.95 ns for row-major, 7.27× slower with an identical checksum.

2. How did array size affect the difference between the two traversal orders? The penalty appears only once the working set outgrows a cache level: - 1 KiB and 64 KiB (fit in L1): 1.00×. Every access hits L1 regardless of order. - 4 MiB (exceeds L1, fits in L2): 1.31×. Column-major misses L1, but the misses are served quickly from L2. - 64 MiB and 256 MiB (exceed L2): 7.27× and 7.51×. Column-major misses L1 on nearly every access and adds TLB misses, while row-major stays at about 0.95 ns because of prefetching.

3. What is the difference between spatial and temporal locality? Give an example of each from this lab. - Spatial locality: after accessing an address, you soon access nearby addresses, so one cache line serves several accesses. - Example: row-major traversal uses all 32 integers in each 128 B line. - Example: grayRowFixed reads a color row's B, G, R bytes sequentially. - Temporal locality: you access the same address again soon, while it is still cached. - Example: in the streaming pipeline, each grayscale row is written and then read by three consecutive Sobel output rows within about 3W bytes of work. It is reused while still in L1. - Example: horizontally adjacent Sobel outputs re-read 4 of the same 8 neighbors, a few instructions apart.

4. Why are three grayscale rows sufficient for a 3×3 Sobel operator? Output row y (input row y+1) depends only on input rows y, y+1 and y+2, because both kernels span exactly one row above and one row below. Once output row y is done, row y is never needed again, and the next output needs only rows y+1, y+2 and y+3. At any moment only three rows are live.

5. How much intermediate storage does the streaming implementation require as a function of width? 3W bytes: three rows of W one-byte grayscale pixels, independent of height. That is 0.94 KiB at 320 wide and 22.5 KiB at 7680 wide, both small enough for L1.

6. How much intermediate storage does the baseline require as a function of width and height? W × H bytes, the full grayscale frame: 56 KiB at 320×180, 7.9 MiB at 4K, and 31.6 MiB at 8K.

7. Does streaming perform fewer arithmetic operations, fewer memory operations, or both? - Arithmetic: identical. WH grayscale conversions and (W−2)(H−2) Sobel evaluations, using the same kernel functions. - Load/store instructions: essentially identical. Each grayscale pixel is still stored once and loaded about 8 times. - What changes is where those accesses go. The grayscale stores and loads target a 3W-byte buffer that stays in L1, rather than a WH-byte frame that at high resolution must travel out to L2 or DRAM and back. - Streaming therefore reduces memory traffic beyond L1 by about 2WH bytes per frame (about 66 MB at 8K), not the number of memory instructions.

8. How did the performance difference change as resolution increased? It barely changed. Speedups were 1.008–1.030× at every resolution, and the second run gave 0.969–1.011×. There is no clear upward trend with resolution. The largest resolution, where the full frame exceeds L2, was about 1.02× in one run and 1.005× in the other. Time per pixel for both implementations stayed at about 10.2–11.6 ns (across both runs) over a 576× range in pixel count.

9. Did reducing the intermediate working set produce the speedup you predicted? Explain using evidence. No. I expected a noticeable speedup at least at 8K, where the grayscale frame cannot stay in cache. The measurements show why it didn't happen: - The pipeline is limited by computation, not memory, at -O0. Each output pixel costs about 10.5 ns, roughly 35 cycles of instructions: address arithmetic, loads, multiplies, shifts, abs, min, all unoptimized. - The pipeline needs about 6 bytes of unique data per pixel. - That is about 0.6 GB/s, a tiny fraction of the M2's memory bandwidth of roughly 100 GB/s. - Eliminating 2 of those 6 bytes per pixel saves memory time that was never the bottleneck. - The baseline already has excellent spatial locality. It writes and reads the grayscale frame strictly sequentially. Part 2 showed that sequential access runs at about 0.95 ns/element even on a 256 MiB array, because the prefetcher hides DRAM latency. - The L2 is large. Up to 4K, the entire grayscale frame (7.9 MiB) fits in the 16 MiB L2, so the baseline's re-read is mostly L2 hits anyway. - Contrast with Part 2: the 7× penalty appeared only with large strides that defeat both cache lines and the prefetcher. The baseline pipeline never does that. - The Part 3 result supports the same conclusion: removing instruction overhead (.at() calls) gave 2.7×, while removing memory traffic gave about 1%. At -O0, instructions dominate.

10. What additional costs or complexity did streaming introduce? - A prime step for the first two rows, plus pointer rotation every row (a few instructions per row, which is negligible). - Harder-to-verify code: the rotation order and the final-use timing of each buffer must be exactly right, or rows are silently overwritten early. - The stages are fused, so the grayscale and Sobel stages can no longer be timed separately. - There is no complete grayscale frame to inspect, display, save or debug. - The stages are coupled: changing the Sobel kernel size (for example to 5×5) requires changing the number of row buffers and the priming logic.

11. When might retaining a complete grayscale image still be the better design? - When the grayscale image has multiple consumers: displayed, saved, or used by other filters, histograms or feature detectors. - When a later stage needs non-local or random access, such as a large kernel, image pyramid or multiple passes. - When the frame fits in cache anyway, as at 4K and below on this M2, so streaming buys nothing. - When using library routines that expect whole cv::Mat images. - When parallelizing, since independent full-frame stages are simpler to split across threads. - When clarity and debuggability matter more than a ~1% gain.

12. Why might -O3 change the relative performance? (prediction) - At -O3 the compiler will inline the row kernels, keep values in registers, remove redundant address arithmetic, and likely auto-vectorize both loops to process 16 pixels per instruction. - That could cut per-pixel compute time by roughly 5–10×. Memory traffic would stay the same, so it would become a much larger fraction of runtime. - The pipeline would shift from compute-bound toward memory-bound. The 2WH bytes per frame that streaming eliminates would then matter. - I therefore predict that streaming will show a larger speedup at -O3 than at -O0, especially at 8K, where the baseline's grayscale frame must round-trip through DRAM. - Separately, I predict the .at() vs ptr() gap will nearly disappear at -O3 because .at() will be inlined.

Conclusion

Central question: can performance be improved by reorganizing when and where data is accessed, with the math unchanged?

Yes, when memory access is the bottleneck. Changing only traversal order made the large-array experiment up to 7.5× faster.

For this image pipeline at -O0, reorganizing data flow gave at most a few percent: - Streaming cut intermediate storage from WH to 3W bytes and eliminated about 2WH bytes of memory traffic per frame, but the pipeline is compute-bound. - The baseline's access pattern was already sequential and prefetch-friendly, and the grayscale frame fits in L2 up to 4K. - The largest measured win in the pipeline came from reducing per-access instruction overhead (ptr() instead of .at(), 2.7×), which is not a cache effect. - Whether a memory optimization pays off depends on whether memory is actually the bottleneck, which I expect to test at -O3.
